# 自動生成機能 補足資料

> 作成日: 2026-09-01  
> 上位仕様: `docs/PROJECT_PLAN.md`

## 結論

時間割の自動生成は、画面ボタン・API・候補配置ロジックを備えた**部分実装**である。現行仕様で求める完成状態には達していない。

`docs/archive/` 配下には自動生成コアを「完了」とする過去資料があるが、仕様・進捗判断では `PROJECT_PLAN.md` を優先する。

## 現在あるもの

- `POST /api/timetables/generate`
- 時間割画面の「自動生成」ボタン
- 科目ごとの必要コマ数をもとに候補を作る処理
- 教員の担当可能科目、出勤不可時間、教員・教室の同時刻重複を考慮する処理
- 候補を探索して配置するバックトラック処理

主な実装箇所は以下である。

- `backend/services/timetable_generator.py`
- `backend/routes/timetables.py`
- `frontend/js/timetables.js`
- `frontend/pages/timetables.html`

## 現行仕様との差分

| 項目 | 現状 | 完成条件 |
|---|---|---|
| 生成成功 | 候補をDBへ保存できる | 科目ごとの必要コマ数を必ず満たす |
| 生成不能 | APIが例外を受けてHTTP 500を返す | HTTP 422と科目別の不足理由を返す |
| 既存時間割 | 成功候補の保存時に全件置換する | 生成不能・保存失敗時は既存時間割を保持する |
| 結果表示 | 生成件数またはエラー文字列のみ | 成功件数、科目別充足、不足理由を画面表示する |
| テスト | テストファイルはあるが、現状はアプリケーションコンテキスト不足で失敗する | 正常系・NG時間・重複・生成不能・既存データ保持を自動テストする |

## 実装見積もり

前提: 現在のモデル・CRUD・認証を土台として維持する。教員本人用時間割画面は含めない。

| 作業 | 見積もり |
|---|---:|
| HTTP 422と不足理由レスポンスの整備 | 0.5人日 |
| 既存時間割を保護するトランザクション処理 | 0.5人日 |
| 制約ロジック・探索処理の仕上げ | 1〜1.5人日 |
| 生成結果・不足理由のUI表示 | 0.5〜1人日 |
| API・結合テストの整備 | 1.5〜2.5人日 |
| **合計** | **4〜6人日** |

`/api/my/timetable` と教員用画面まで含める場合は、さらに2〜3人日を見込む。自動生成関連を現行計画どおり完成させる総量は、6〜9人日を目安とする。

## 完了判定

以下を満たした時点で、自動生成機能を完成とする。

1. 科目ごとの必要コマ数と生成件数が一致する。
2. 担当外教員、出勤不可時間、教員・教室の同時刻重複を含まない。
3. 生成不能時はHTTP 422と科目別不足理由を返す。
4. 生成不能・保存失敗時も、直前の時間割は残る。
5. 成功・失敗の内容を時間割画面で確認できる。
6. 上記を自動テストで確認できる。

## 注意点

- 現在のDBには、過去の時間割データで `subject_id` が未設定の行が残り得る。生成前に科目・担当可能科目を設定し、必要に応じて時間割を整理する。
- バックトラック探索はデータ量・制約数が増えると計算時間が増える。実データ規模での上限時間と、探索打ち切り時の扱いを決める必要がある。
