# 時間割・教室自動割り当てシステム 現行計画書

> 更新日: 2026-08-25  
> この文書を **現行仕様・進捗・作業計画の唯一の基準** とする。  
> 過去の計画書・進捗資料・チーム別指示書は `docs/archive/` に保存し、仕様判断には原則使用しない。

---

## 1. プロジェクト概要

学校向けの「時間割・教室管理および自動割り当てシステム」を開発する。

現在の構成は以下を基本とする。

- Backend: Python / Flask / SQLAlchemy
- Frontend: HTML / CSS / JavaScript
- DB: 開発環境と本番環境を分けて運用する想定
- 主な既存機能: 教員CRUD、教室CRUD、時間枠CRUD、時間割CRUD、週間カレンダー表示、自動生成

既存の自動生成機能は動作するが、現在の教員要求を満たすにはロジックとデータモデルの大幅な拡張が必要である。

---

## 2. 現在の最優先要件

教員から追加された要求は次の3点である。

1. **教員の出勤不可条件を設定できること**
   - 「この曜日は不可」のような終日NG
   - 「この曜日の何時間目は不可」のような特定時限NG

2. **教員が自分に割り当てられた教室を確認できること**
   - 教員がログインする
   - 自分の授業だけを表示する
   - 曜日、時限、科目、割当教室を確認できる

3. **科目ごとの必要コマ数を確実に満たすこと**
   - 科目ごとに週当たり必要コマ数を登録する
   - 自動生成成功時は必要コマ数と割当数を一致させる
   - 条件上不可能な場合は無理に保存せず、不足理由を返す

この3点を現在の開発の中心要件とする。

## 3. 一本化時に採用した仕様

過去文書には複数の設計案が混在していたため、以下を現行仕様として採用する。

### 3.1 必要コマ数

過去案には `Teacher.required_periods` を持たせる設計もあったが、要求は「**科目ごとのコマ数**」であるため採用しない。

現行仕様:

```text
Subject.required_periods_per_week
```

科目単位で必要コマ数を管理する。

### 3.2 教員と科目

教員が担当可能な科目を管理するため、中間モデルを設ける。

```text
TeacherSubject
- teacher_id
- subject_id
```

自動生成では担当可能な教員だけを候補にする。

### 3.3 出勤不可条件

名称は **TeacherUnavailability** に統一する。

```text
TeacherUnavailability
- id
- teacher_id
- day_of_week
- period
```

- `period = NULL`: その曜日を終日不可
- `period = 1〜5`: その曜日の特定時限のみ不可

例:

```text
Tuesday / NULL  -> 火曜日は終日不可
Thursday / 3    -> 木曜日3限は不可
```

### 3.4 時間割

既存の `Timetable` に `subject_id` を追加する。

最低限、1件の時間割は以下を持つ。

```text
Timetable
- teacher_id
- subject_id
- classroom_id
- day_of_week
- period
```

### 3.5 ユーザーと認証

`Teacher` にパスワードを直接持たせず、ログイン用の `User` を分離する。

```text
User
- id
- username
- password_hash
- role
- teacher_id
- is_active
```

役割は当面以下の2種類とする。

- `admin`: 管理者
- `teacher`: 教員

教員ユーザーは `Teacher` と紐付ける。

### 3.6 本人用時間割API

本人の時間割取得は以下に統一する。

```text
GET /api/my/timetable
```

クライアントから任意の `teacher_id` を指定して本人判定を行わず、ログインユーザーに紐付く教員IDをサーバー側で使用する。

### 3.7 認証方式

現行計画では HTTP-only セッションCookieを基本方針とする。

管理APIは管理者のみ、本人用時間割はログイン教員が利用できるようにする。

### 3.8 オンライン授業均等化

過去スプリントで BI015 として実装された機能だが、今回追加された3要求には含まれていない。

**現在の最優先改修では新生成ロジックの必須条件から外し、後で必要性を再確認する。**

既存カラム・表示を削除するかどうかは互換性を確認してから判断する。

## 4. 現在のデータモデル目標

```text
User
  └── teacher_id ─────────────┐
                              ▼
                           Teacher
                              │
              ┌───────────────┴──────────────┐
              ▼                              ▼
   TeacherUnavailability               TeacherSubject
                                             │
                                             ▼
                                           Subject
                                             │
                              required_periods_per_week

Timetable
 ├── teacher_id
 ├── subject_id
 ├── classroom_id
 ├── day_of_week
 └── period
```

追加・変更する主なモデル:

| モデル | 主な項目 | 主な制約 |
|---|---|---|
| `User` | username, password_hash, role, teacher_id, is_active | username一意、teacherユーザーはteacher_id必須 |
| `Subject` | name, required_periods_per_week | name一意、必要コマ数1以上 |
| `TeacherSubject` | teacher_id, subject_id | 組み合わせ一意 |
| `TeacherUnavailability` | teacher_id, day_of_week, period | 同一条件の重複禁止 |
| `Timetable` | 既存項目 + subject_id | 教員・教室の同時刻重複禁止 |

## 5. API目標

| API | 用途 | 権限 |
|---|---|---|
| `POST /api/auth/login` | ログイン | 未認証 |
| `POST /api/auth/logout` | ログアウト | ログイン済み |
| `GET /api/auth/me` | ログインユーザー取得 | ログイン済み |
| `/api/users` | ユーザーCRUD | 管理者 |
| `/api/subjects` | 科目・必要コマ数CRUD | 管理者 |
| `/api/teachers/<id>/subjects` | 教員の担当可能科目 | 管理者 |
| `/api/teachers/<id>/unavailable-slots` | 曜日/時限NG管理 | 管理者 |
| `GET /api/my/timetable` | 自分の時間割・割当教室取得 | 教員 |
| `POST /api/timetables/generate` | 自動生成 | 管理者 |

生成不能の場合は HTTP 422 を使用し、どの科目が何コマ不足したか、可能であれば理由も返す。

## 6. 自動生成エンジンの完成条件

現行の単純なラウンドロビン生成は置き換える。

新しい生成器は最低限、以下をすべて守る。

1. 科目ごとの必要コマ数を厳密に満たす
2. 担当可能な教員だけを割り当てる
3. 教員の終日不可を守る
4. 教員の特定時限不可を守る
5. 同じ教員を同じ曜日・時限に重複配置しない
6. 同じ教室を同じ曜日・時限に重複使用しない
7. 複数教室がある場合、同一時限に複数授業を配置できる
8. 条件を満たせない場合は失敗として扱う
9. 失敗時に既存時間割を消さない

### 生成処理の基本方針

```text
DBの既存時間割を先に削除しない
        ↓
メモリ上で候補時間割を作成
        ↓
全制約を検証
        ↓
成功 -> トランザクションで既存時間割と置換
失敗 -> 422 + 不足理由、既存時間割は保持
```

配置順は、候補枠が少ない科目・制約の厳しい科目を優先する。

## 9. 現在の注意点

### 9.1 DB変更

`db.create_all()` は新しいテーブルを作成できるが、既存テーブルへのカラム追加を自動で安全に行う仕組みではない。

`Timetable.subject_id` など既存テーブルを変更するため、開発DBを作り直すか、マイグレーション手段を用意する。

### 9.2 テスト

新機能に入る前に、既存テストとseed処理の前提を統一する。

目標コマンド:

```bash
python -m unittest discover -s backend/tests
```

新機能着手時点でこれが成功する状態を目標にする。

### 9.3 旧 `Teacher.subject`

既存の `Teacher.subject` 文字列は移行用として扱い、今後の正式な科目判定は `Subject` と `TeacherSubject` を正とする。

## 11. 2チームでの作業分担

5人で作業する場合は、原則 **3人 + 2人** の2チームに分ける。

| チーム | 人数目安 | 主担当 |
|---|---:|---|
| チームA | 3人 | DB・データモデル、認証・権限、管理API、管理者UI、基盤テスト |
| チームB | 2人 | 自動生成エンジン、本人時間割API、教員UI、結合・受入テスト |

詳細な担当範囲と生成AI向け指示は以下を正とする。

```text
docs/TEAM_A.md
docs/TEAM_B.md
```

両チーム文書は本書を上書きする仕様書ではなく、**本書を実装するための作業指示書**である。
仕様が衝突した場合は `docs/PROJECT_PLAN.md` を優先する。

Git運用方法そのものはこれらの文書では規定しない。
同一ファイルを両チームが同時に大きく変更しないよう、担当境界を優先する。

## 12. 受入テスト

最低限、以下をデモで通す。

1. 管理者が科目Xを週3コマ、科目Yを週2コマとして登録する。
2. 教員AにX、教員BにYを担当可能科目として設定する。
3. Aに「火曜終日不可」と「木曜3限不可」を設定する。
4. 自動生成する。
5. Xが3コマ、Yが2コマ割り当てられていることを確認する。
6. Aが火曜および木曜3限に配置されていないことを確認する。
7. 教員・教室の同時刻重複がないことを確認する。
8. Aでログインし、A本人の曜日・時限・科目・割当教室だけが表示されることを確認する。
9. 必要コマ数を物理的に配置不可能な値へ変更して生成する。
10. 422と不足理由が返り、直前の正常な時間割が消えていないことを確認する。
