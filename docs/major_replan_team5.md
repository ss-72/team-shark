# 大幅改修：5人チーム向け計画書・指示書

作成日: 2026-07-21  
対象: 現行 Flask + SQLAlchemy / HTML + JavaScript の時間割管理システム

## 1. 今回の到達点

次の三点を、一連の操作として成立させる。

1. 管理者がユーザー（教員に紐付くログインアカウント）を管理できる。
2. 教員がログインすると、**自分が担当する授業で割り当てられた教室**を、曜日・時限・科目・教室名の表で確認できる。
3. 自動生成が、教員の不可条件と科目ごとの必要コマ数を必ず検証する。全科目の必要コマ数を満たせない場合は、不足理由を返し、矛盾した時間割を保存しない。

### スコープ上の前提

- ユーザーは当面「管理者」と「教員」の二役割とする。教員ユーザーは `Teacher` に一対一で紐付ける。
- 不可条件は「終日不可（例: 火曜は不可）」と「特定時限不可（例: 木曜3限は不可）」を扱う。曜日のみの条件は、その曜日の全時限に展開して判定する。
- 科目には週当たり必要コマ数を持たせる。時間割の各行には必ず科目を持たせ、同一科目の時間割行数が必要コマ数と一致することを完成条件とする。
- 初回は、1コマにつき担当教員1人・教室1室・科目1つとする。複数教員担当、学年/クラス、連続コマ、教室の定員最適化は今回の対象外。
- 既存の「オンライン自動割当」は新要件に含まれないため、生成対象から外す（既存列を残すかは移行担当が互換性を確認して判断する）。

## 2. 完成イメージと権限

| 利用者 | できること | 見える表 |
|---|---|---|
| 管理者 | ユーザー、教員、科目、教員不可条件、教室、時間割を管理。自動生成を実行し、結果・不足理由を確認 | 全教員・全教室の時間割 |
| 教員 | ログイン、本人の時間割閲覧 | 曜日 / 時限 / 科目 / 割当教室（必要なら担当教員名） |

教員画面の主目的は「空き教室一覧」ではなく、**本人の授業に割り当て済みの教室一覧**である。表示対象はログインユーザーに紐付く `teacher_id` の時間割だけに限定する。

## 3. データ・APIの共通契約（担当着手前に固定）

### 3.1 最低限のデータモデル

| モデル | 主な項目 | 制約 |
|---|---|---|
| `User` | `id`, `username`, `password_hash`, `role`, `teacher_id`, `is_active` | `username` は一意。`role=teacher` は `teacher_id` 必須かつ一意。パスワード平文は保存しない |
| `Subject` | `id`, `name`, `required_periods_per_week` | `name` は一意。必要コマ数は 1 以上の整数 |
| `TeacherSubject` | `teacher_id`, `subject_id` | 複合一意。担当可能な教員だけを生成候補にする |
| `TeacherAvailability` | `id`, `teacher_id`, `day_of_week`, `period` | `period=NULL` は終日不可、数値は当該時限不可。同一条件を重複登録しない |
| `Timetable`（拡張） | 既存項目 + `subject_id` | `subject_id` は必須。教員・教室・曜日・時限の既存重複制約を維持 |

曜日値は既存に合わせ `Monday`〜`Friday`、時限は `TimeSlot` に登録済みの `period` のみ使用する。科目別必要コマ数の集計は `Timetable.subject_id` を正とし、教員の既存 `subject` 文字列は移行期間のみ参照する。

### 3.2 API方針

認証済みリクエストを前提にし、管理系APIは管理者のみに制限する。認証方式は HTTP-only セッションCookieを採用し、フロントは API と同一オリジンで配信する（少なくとも本番では `file://` 起動を禁止）。

| API | 用途 | 権限 |
|---|---|---|
| `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me` | ログイン状態 | 未認証 / 本人 |
| `/api/users` | ユーザーCRUD、教員との紐付け | 管理者 |
| `/api/subjects` | 科目CRUD、必要コマ数 | 管理者 |
| `/api/teachers/<id>/subjects` | 担当可能科目の設定 | 管理者 |
| `/api/teachers/<id>/unavailable-slots` | 終日・時限別不可条件CRUD | 管理者 |
| `GET /api/my/timetable` | ログイン教員の割当教室を含む時間割 | 教員 / 管理者 |
| `POST /api/timetables/generate` | 制約を満たす生成 | 管理者 |
| `GET /api/timetables/generation-report` または生成レスポンス | 科目別の充足数・不足理由 | 管理者 |

`POST /api/timetables/generate` の成功レスポンスには、少なくとも `status`, `timetables`, `subject_summary`（`subject_id`, `required`, `assigned`）を含める。実現不能なら HTTP 422 と `unassigned`（科目、残数、理由）を返し、DBの時間割は変更しない。通常の時間割CRUDでも、不可枠違反と科目担当外の組合せを 409/422 として拒否する。

## 4. 実装順序と5人の担当

同じファイルを同時に編集しないため、最初に担当1がスキーマ/API契約をPRにし、他担当はそこへ依存する形で作業する。全員が機能ブランチを作成し、mainへ直接pushしない。

| 担当 | 主担当 | 成果物 | 着手条件 |
|---|---|---|---|
| 1. 基盤・認証 | `User`、ログイン/権限、DB移行、同一オリジン化 | 認証基盤PR | 最優先 |
| 2. 管理データAPI | 科目、教員-科目、不可条件、既存時間割の検証拡張 | 管理API PR | 担当1のモデル契約後 |
| 3. 生成ロジック | 制約充足生成、ロールバック、充足/不足レポート | 生成器PR・単体テスト | 担当2のAPI/モデル契約後 |
| 4. 管理画面 | ログイン、ユーザー/科目/不可条件の管理UI、生成結果表示 | 管理UI PR | 担当1・2のAPIモックで並行可 |
| 5. 教員画面・品質 | 本人用「割当教室表」、E2E/API回帰試験、受入確認 | 教員UI・テストPR | 担当1・3の結合後 |

### 担当1: 基盤・認証（リード兼結合窓口）

- `User` モデル、パスワードハッシュ、初期管理者作成手順を実装する。
- `@login_required` と `@admin_required` を共通化し、認証/認可を全APIに適用する。`GET /api/my/timetable` はサーバー側で本人の `teacher_id` を決め、クエリ文字列のIDを信用しない。
- 開発・本番ともフロントを同一オリジンで提供できる構成に直す。Cookie利用時は `CORS(app)` の全許可を残さない。
- SQLite/MySQL双方で作動するマイグレーション手順を文書化し、既存データからの移行方針（既存教員に科目を作る、既存時間割の `subject_id` を補完または再生成）を明記する。
- 所有ファイルの目安: `backend/app.py`, 認証用 route/service/model, DB移行資料, 認証テスト。

受入条件: 未ログインで保護APIは401、教員が管理APIを呼ぶと403、パスワードがDB/API応答に出ない、教員が別教員の時間割を取得できない。

### 担当2: 管理データAPI・手入力整合性

- `Subject`、`TeacherSubject`、`TeacherAvailability` を実装し、CRUD APIと入力検証を作る。
- 終日不可と時限不可を重複なく保存し、一覧ではUIが扱いやすい形で返す。曜日・時限は `TimeSlot` と整合する値だけ受け付ける。
- `Timetable` に `subject_id` を追加し、作成・更新時に「担当可能科目」「不可枠」「教員/教室重複」を検証する。
- 既存の `routes/timetables.py` の作成処理に未完成箇所があるため、この担当でPOST/GET/PUT/DELETEの正常系・異常系を通す。
- 所有ファイルの目安: `backend/models/subject.py`, `teacher_subject.py`, `teacher_availability.py`, `backend/routes/subjects.py`, `backend/routes/teachers.py`, `backend/routes/timetables.py`。

受入条件: 管理者が「火曜終日不可」「木曜3限不可」を登録でき、その枠への手動登録が拒否される。科目ごとに必要コマ数を保存でき、担当外教員での登録が拒否される。

### 担当3: 自動生成ロジック

- 現行のラウンドロビン生成を置換する。生成候補は `TeacherSubject` と教員不可枠を必ず反映し、教員・教室の同時刻重複を禁止する。
- まず残り候補が少ない科目（必要コマ数が大きい、担当教員の空きが少ない科目）から配置する。候補不足時に理由を記録する。
- 生成前にメモリ上で全割当を作り、全科目が必要コマ数に達した場合だけ一つのトランザクションで既存時間割を置換する。失敗時は既存時間割を消さない。
- 生成後に独立した検証関数で、科目別コマ数、不可枠、教員重複、教室重複を再チェックする。
- 所有ファイルの目安: `backend/services/timetable_generator.py`, 生成専用テスト。`routes/timetables.py` の生成エンドポイントは担当2と編集順を調整する。

受入条件: 成功時は全科目が `assigned == required`。不可能なケースは422・不足理由を返し、生成前の時間割が残る。いずれの結果にも同一教員/教室の同時刻重複がない。

### 担当4: 管理画面

- ログイン画面とログアウト、管理者だけに管理メニューを表示する導線を実装する。
- ユーザー管理（ユーザー名、役割、紐付け教員、有効/無効）、科目管理（必要コマ数）、教員ごとの担当科目・不可条件を入力できる画面を作る。
- 不可条件UIは「曜日全体」と「曜日＋時限」を明確に選べ、登録済み条件の削除もできること。
- 自動生成の結果には科目別の `必要 / 割当 / 差分` と、失敗時の不足理由を表で出す。成功/失敗のどちらでも画面上で判別できること。
- 所有ファイルの目安: `frontend/index.html`, `frontend/pages/*`, `frontend/js/*`, `frontend/css/style.css`。既存ファイルの編集競合は担当5と事前に分ける。

受入条件: 管理者がブラウザだけで、科目・必要コマ数・担当可能教員・不可条件を設定して生成結果を確認できる。

### 担当5: 教員用表示・品質保証

- ログイン後、教員を `/api/my/timetable` へ誘導する。表示は曜日→時限で安定ソートした表とし、列は「曜日、時限、科目、割当教室」。データなしも明確に表示する。
- URLや画面上の選択値を書き換えても、他人の割当教室が表示されないことを確認する。
- APIテストを役割別に分割し、認証、不可枠、科目コマ数、生成成功/失敗、本人表示を自動テスト化する。必要ならブラウザの手動受入手順も `docs/` に残す。
- 既存機能の回帰（教員、教室、時限、時間割のCRUD）を実施し、既存テストの壊れた前提は新仕様に沿って更新する。
- 所有ファイルの目安: 教員専用HTML/JS、`backend/tests/`、受入試験資料。

受入条件: 教員でログインすると自分の割当教室だけが表に出る。管理者でログインすると全体表示と管理画面にアクセスできる。自動テストが全件成功する。

| 日 | 全体のゲート | 担当別の主作業 |
|---|---|---|
| 1日目 | 契約確定・DB設計レビュー | 1: 認証の土台、2: モデル/API仕様、3: 生成器のテストケース設計、4/5: 画面ワイヤーとAPIモック |
| 2日目 | 管理データを登録可能にする | 1: 権限、2: CRUD・手入力検証、3: 制約判定関数、4: 管理UI、5: 本人表示の骨組み |
| 3日目 | 生成APIの結合 | 3: 原子生成・レポート、4: 結果表示、5: API統合試験、1: 認証結合・移行確認 |
| 4日目 | 失敗ケースを含むE2E | 全員: 受入ケース実施、競合・表示・エラー文言の修正 |

日次15分の同期では「API変更予定」「編集ファイル」「ブロッカー」「当日中にレビューが必要なPR」を必ず共有する。データモデルまたはレスポンス形式を変えるPRは、担当1・2・3のうち少なくとも1人のレビューを必須にする。

## 6. 受入テスト（デモで必ず実施）

1. 管理者でログインし、教員A/B、教室、時限、科目X（週3コマ）/Y（週2コマ）を用意する。
2. AにX、BにYを担当可能科目として設定する。Aに「火曜終日不可」と「木曜3限不可」を登録する。
3. 自動生成を実行する。Xが3、Yが2コマであること、Aが火曜および木曜3限にいないこと、教員・教室の重複がないことを確認する。
4. Aのユーザーでログインし、「曜日・時限・科目・割当教室」の表にAの行だけが表示されることを確認する。
5. Xの必要コマ数を、利用可能な枠数より大きく変更して再生成する。422と不足理由が表示され、手順3で作成した時間割が消えていないことを確認する。
6. 教員アカウントでユーザー管理・科目管理・生成APIを開こうとして拒否されることを確認する。

## 7. Definition of Done

- 上記6件の受入テストをすべて通過している。
- 必要コマ数は「可能な限り」ではなく、成功時にすべて厳密一致している。満たせない生成は保存しない。
- 不可条件は手動登録と自動生成の両方で守られる。
- パスワード平文、全許可CORS、クライアント指定の教員IDによる本人判定を残さない。
- DB更新手順、初期管理者の作り方、テスト実行手順、既存データの移行方針を `README.md` または `docs/` に記載している。
- CI相当のテストコマンド（例: `python -m unittest discover -s backend/tests`）が成功し、レビュー済みPRのみを結合している。

## 8. 着手前に教員へ確認する事項（未確認のため仮定した点）

以下は要件の幅が大きく、実装前または初日の設計レビューで確認する。

1. 「ユーザー」は教員だけか、事務職員・管理者も個別アカウントを持つか。
2. 科目は担当教員を一人に限定してよいか。複数担当、学年/クラス別、同一科目の複数並列授業が必要か。
3. 必要コマ数は週単位でよいか。曜日分散、連続授業、午前/午後、教室定員・専用教室などの追加制約があるか。
4. 既存のオンライン授業・フロア別時限・優先学科の要件を引き継ぐか、今回の仕様から外すか。

確認結果が出るまでは、本書の「一人の担当教員・週単位・教員不可枠のみ」を実装基準とする。
